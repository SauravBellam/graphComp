# Notebook 19: teacher trajectories → 31B LoRA + two students → holdout comparison → submission (Oct 15)

Notebook: `19_teacher_lora31_student_holdout_submission.ipynb`, generated by
`scripts/planB/notebook_builder/make_nb19.py` (re-run it after editing `run_arm.py`, `build_rft_data.py` or `train_lora.py`;
all three are embedded). It replaces the TPU notebooks T1/T2 (`../TPU_runs/`) and the never-run notebook 18. Nothing here has
run on Kaggle yet: every number below is either measured earlier (with its source) or labelled an estimate.

## 1. Why this notebook exists

- **TPU is out.** Kaggle TPU v5e-8 queues were too long. The teacher-data job of T2 moves to the 4 × L4 GPUs, where it is
  better data anyway. The teacher is the scoring model itself (w4a16, not the unquantized twin), requests carry a seed, and
  vLLM enforces the thinking budget (none of the three held on TPU, see `../TPU_runs/README.md`).
- **Budget.** About 15 Kaggle GPU hours remain. The notebook must stay under 14, and a Kaggle session stops at 12, so every
  stage resumes from an attached earlier output.
- **Offline.** Internet is off. The only things not in the Kaggle image are two pure-Python wheels: peft 0.21.2 and
  accelerate 1.15.0, the versions that trained the E4B adapter on the VM. They ship as the private dataset
  `graphcomp-train-wheels` (`../graphcomp-train-wheels/`). Without it the image's peft 0.19.1 / accelerate 1.13.0 are used.
- **Two goals in one run:** (a) more teacher trajectories; (b) a submission chosen by a measured comparison, not by validation
  loss.

## 2. What the VM run did and did not show (Oct 14-15)

- The first E4B LoRA (`~/gc/lora/rft_e4b_v1`, 17 trajectories) trained to val loss 0.374 → 0.232.
- Its dev-slice evaluation never ran. `dev_runs.py` passed `--limit-mm-per-prompt image=0,audio=0`, which vLLM 0.19.1 rejects.
- More important, the VM's vLLM (PyPI 0.19.1) refuses LoRA on Gemma 4 outright: `Gemma4ForConditionalGeneration does not
  support LoRA yet` (test on the VM, Oct 15). Only Kaggle's competition build serves adapters: notebook 14 started 31B with
  `--enable-lora` and the sample adapters. **Adapters can only be evaluated on Kaggle.**
- So there is no resolution evidence for any adapter yet; validation loss is not that evidence. Notebook 19 measures
  resolution on a holdout. Before any LoRA arm, it probes whether vLLM actually applies the adapter: one greedy request to
  the base and one to the adapter, which must differ.

## 3. Pipeline and the reasoning behind each choice

### 3.1 Teacher trajectories (≤ 4.6 h)
- **Model and agent.** The 31B competition model runs the exact agent that will be submitted: sample prompt + budget section,
  nine tools, `max_output_tokens` 8192, thinking 4096.
- **Why the deployed agent rather than notebook 01's B2 condition:** train = deploy (section 3.3). The trajectories then
  already show budget-aware behaviour: early edits, `get_status` checks.
- **Tasks:** the 53 valid tasks in neither official slice. That is 56 minus the 3 moved into the holdout (section 3.5).
- **Seeds:** 11, 12 and 13, plus notebook 01's seed-1 run on the same tasks. Data quantity matters more than filtering at
  this scale (section 3.3).
- **Caps inside the notebook: 8 minutes and 30 calls at concurrency 4.** That is about the deployed 5 minutes run alone. The
  1.6× concurrency slowdown is an estimate, not a measurement.
- **Data build.** `build_rft_data.py` keeps resolved trajectories on Kaggle-valid tasks, at most 3 per task, and refuses
  dev/holdout tasks. Notebook 19 also drops the 3 added holdout tasks, which notebook 01 ran at seed 1.

### 3.2 The deployment budget (the 12-hour limit)
- **How scoring runs.** The hidden set has "about 120 tasks" (rules). They run one after another: swegemma's `EvalConfig`
  concurrency defaults to 1. The 12 hours include sandbox setup, and a submission can set only per-task caps
  (`eval_config.yaml`).
- **The cap.** Following the requirement that the run must finish even if every task hits its cap:
  `(720 − 15 min serving start − 20 min margin) / 120 − 0.5 min setup = 5.2 → 5 minutes`, 30 tool calls, 80 turns, 240-s
  command timeout. Worst case: 120 × 5.5 + 15 = 675 min ≈ 11.3 h, plus the 20-minute margin. The formula is in the config
  cell (`N_TASKS_ASSUMED`), and an `assert` keeps any edit inside 12 h.
- **Cost of 5 minutes (measured).** In notebook 01 (B2_s1, 31B, concurrency 4), 23 of 40 resolved tasks made their last
  edit within 5 minutes and 31 of 40 within 8; 29 of 40 within 28 calls. Edit times are estimated from each trace's call
  order and the task's duration (traces have no timestamps). Alone, tasks run faster, and the prompt pushes edits earlier.
- **Making the agent budget-aware with what the harness offers.**
  - `get_status` is free (it does not count as a tool call) and returns `time_seconds_remaining` (HARNESS_README §5).
  - The harness warns at ≤ 10 calls left.
  - On a timeout the working tree is graded as a fallback patch (`agent_runner.py`). An unsubmitted edit still counts.
  - The prompt section therefore says: check `get_status` every 4-5 calls; edit by 40% of the time; with < 30% left, run one
    test and submit; with < 60 s left, submit now.
- **Output reserve.** `max_output_tokens` 8192 instead of 16384 leaves 24k tokens of input. Context-exceeded endings were the
  largest single loss in B2_s1 (16 valid tasks, 0 resolved; `plan_b_results.md` §1).
- **Per-task caps.** Lower caps for "known bad" problems cannot be set per task: `eval_config.yaml` is global, and the hidden
  tasks come from unknown private repositories.
- **Compared with a public notebook.** A public Kaggle notebook uses 8 minutes and 28 calls, and notes that 8 minutes "is not
  a guarantee of the global 12-hour limit" ([Gemma 4 SuperAgent](https://www.kaggle.com/code/matterhorn3838/gemma-4-superagent);
  local copies in `../../../Other/`). We chose the guaranteed bound instead.

### 3.3 LoRA training (`scripts/planB/lora/train_lora.py` v2)

| Choice | Why | Source |
| --- | --- | --- |
| Loss on assistant turns only, whole conversation as context | standard multi-turn tool-calling SFT | SFT or RL for Tool-Calling Agents? [2609.17848](https://www.alphaxiv.org/abs/2609.17848) |
| Turns packed into windows (≤ 2,500 target tokens E4B/12B, 8,000 31B), verified turn by turn, per-turn fallback | the same objective, about 10x fewer forward passes; 31B would not fit the time budget otherwise | our engineering (VM test Oct 15: 15 windows, 0 fallbacks) |
| No loss on turns whose tool call returned an error (run_command excepted: test and reproduction failures are feedback) | "step-level error masking" | SWE-Lego [2601.01426](https://www.alphaxiv.org/abs/2601.01426) |
| Recorded system prompt and the harness's budget lines rewritten to the deployed ones | train with the same prompt and serialization as evaluation | [2609.17848](https://www.alphaxiv.org/abs/2609.17848) |
| Up to 3 trajectories per task (was 2), every seed kept | at 500 → 1,000 trajectories, more data lowered held-out loss about 18x more than quality filtering; resolved-only gating was not better than random at 500 | Trajectory Data Curation for LoRA Fine-Tuning of Code Agents [2607.17205](https://www.alphaxiv.org/abs/2607.17205) |
| Vanilla LoRA, rank 32, alpha 64, lr 1e-4, cosine with warmup, ≤ 2 epochs, all language-model projections | LoRA variants reach vanilla LoRA's peak once the learning rate is tuned; the controlled tool-calling study used exactly r32 / α64 / 1e-4 / 2 epochs | Learning Rate Matters [2602.04998](https://www.alphaxiv.org/abs/2602.04998); [2609.17848](https://www.alphaxiv.org/abs/2609.17848) |
| 31B and 12B: no k_proj LoRA on full-attention layers | `attention_k_eq_v`: HF computes V from k_proj there, vLLM copies the base K weights into V but not the LoRA delta → train/serve mismatch | model configs ([31B](https://huggingface.co/google/gemma-4-31b-it-qat-q4_0-unquantized/blob/main/config.json), [12B](https://huggingface.co/google/gemma-4-12b-it-qat-q4_0-unquantized/blob/main/config.json)); HANDOFF Oct 14 |
| `--time-budget-h`: the step count shrinks after step 2 so the schedule still anneals and the adapter is always saved | a Kaggle session that runs out loses its output | our engineering |
| 31B: one process, 4-bit model split over 4 GPUs; students: data-parallel | 31B nf4 (~18 GB) plus activations does not fit one L4 | VM tests Oct 15 on E2B (both modes trained and saved) |

**Teacher vs student.** Fine-tuning on a model's own trajectories lowered SWE-Gym's resolve rate from 15.3% to 8.7%
([SWE-Gym, p. 5](https://www.alphaxiv.org/pdf/2412.21139?page=5)). LORA31 is close to that self-distillation case, while the
students learn from a stronger teacher. That is why BASE31 is in the comparison and wins ties.

### 3.4 Two students, trained and evaluated side by side
- **Why smaller models.** The Oct 13 model announcement:

  > More test time compute: Inference is faster and memory burden lower so you can execute more and longer reasoning turns and
  > iteration cycles. You could also experiment with using ParallelAgent for concurrent LLM calls (though tool calls are still
  > executed sequentially).
  >
  > Faster and more accessible LoRA finetuning: Experiment with different setups more quickly and on more accessible GPUs. [...]
  >
  > More specialized agents: Smaller models use smaller LoRA adapters, so you can include more of them in your submission.

- **What the notebook does with that:**
  - **Training:** E4B on GPUs 0-1 and 12B on GPUs 2-3 at the same time, each with its own torchrun port.
  - **Serving:** each student gets its own vLLM server on one GPU and its own port (8001 and 8002).
  - **Holdout:** both runs happen at once. Each agent still runs its own tool calls one at a time.
- **12B risk.** 12B (`Gemma4UnifiedForConditionalGeneration`) failed to serve in notebook 11 at tp 4 (`Expected hidden_size
  to be 3840, but found: 256`, vLLM's Transformers fallback). Transformers 5.13.1 has `gemma4_unified`, so training should
  work. Serving is tried at tp 1, and a failure only removes that arm. It is recorded as `serve_failed`.
- **ParallelAgent** (concurrent LLM calls inside one submission) is not used yet: it changes the agent itself, and nothing has
  been measured for it. It is a candidate once a student shows it can resolve tasks.

### 3.5 The holdout: every kind of task
- **Official slice.** 24 tasks (seed 20261012): 14 fastapi and 10 rich, all valid on Kaggle, 17 single-file and 7 multi-file.
  Never trained on.
- **Missing categories.** The slice covers 6 of the 9 task categories (Plan B cells = graph distance × visibility). One valid
  task per missing category moves from the training pool into the holdout: fastapi_15661 (d_undef|v_undef), rich_3471
  (d0|v_low) and rich_3718 (d1|v_low). The scored holdout is 27 tasks and covers 9 of 9 categories; the official-24 score is
  reported too.
- **requests and httpx.** requests_6589 and httpx_3672 run as budget and behaviour checks only. In Kaggle's subprocess sandbox
  their tests import the installed library, not `/workspace` (B1 import check), so even the reference patch fails there. Their
  time, call count and patch size are reported, not a resolution.

### 3.6 Choosing the submission
- **The rule.** The arm with the most scored holdout tasks resolved wins; ties go to BASE31, then LORA31, E4B, 12B.
- **Exclusions.** Arms whose adapter vLLM ignored or which failed to serve are excluded.
- **The noise bar.** Two runs of one condition differ by about 3 of 23 tasks (notebooks 14 vs 01). A smaller gap is
  reported but is not evidence.
- **Output.** All candidates get the deployment budget and are kept in `graphcomp_arm/submissions/final_*`.
  `/kaggle/working/submission.zip` is the winner.

## 6. Known risks
- **Untested on Kaggle:** the whole notebook, the 31B training speed (the time budget adapts), 12B serving, and adapter
  serving (guarded by the no-op probe).
- **Student fit:** two student ranks per GPU pair. E4B fit one L4 per rank at 2,500 target tokens on the VM; 12B nf4 is
  larger. If it runs out of memory, only that student fails.
- **The 1.6× concurrency factor is an estimate.** The deployed 5-minute cap is the one that matters for the 12 h limit.
- **Unchecked summaries.** The literature notes in section 3.3 come from alphaXiv summaries for 2609.17848, 2601.01426,
  2607.17205 and 2602.04998, not the full texts. SWE-Gym (p. 5) was read in the original earlier (TPU README).

## 8. Changes after the first draft (Oct 15)
- **31B training placement:** `device_map="balanced"` instead of `"auto"`. "auto" fills GPU 0 first, and the 4-bit 31B (~19 GB) would have
  landed there with no room for activations. Re-tested on the VM (E2B: loads, trains, saves).
- **12B training windows:** at most 1,500 target tokens and 14,336 tokens per window (E4B: 2,500 / 18,432). 12B in 4 bits takes ~9 GB,
  and a full-size window would reach about 20 of 22.5 GB on one L4.
- **Model search:** skips `-assistant` checkpoints (speculative-decoding drafters, not the model).
- **Machine (g2-standard-24: 24 vCPUs, 4 × L4):**
  - Each student runs its holdout at concurrency 4, as the 31B arms do, both at once on separate GPUs.
  - The limit is GPU memory and generation speed, not CPU. The 31B server has a 27,712-token GPU KV cache (notebook 14), so
    concurrency stays at 4 everywhere.
- **Scope cut (Oct 15).** This run is for the submission: BASE31 vs LORA31 on the holdout picks it.
  - **One student, 12B,** trained on all 4 GPUs. Its holdout run is off (`EVAL_STUDENTS = False`); the adapter and a ready
    submission folder are saved for a later test. E4B is a one-line fallback in the config cell.
  - **Inputs:** 3 models: 31B w4a16 (Other), 31B and 12B `-qat-q4_0-unquantized` (Transformers).
- **Why 12B and not E4B.** Google's model card ([gemma-4-12b-it-qat-w4a16-ct](https://huggingface.co/google/gemma-4-12b-it-qat-w4a16-ct)):

  | | 12B | E4B |
  | --- | --- | --- |
  | LiveCodeBench v6 | 72.0% | 52.0% |
  | Codeforces ELO | 1659 | 940 |
  | Tau2, agentic tool use | 69.0% | 42.2% |
  | MMLU Pro | 77.2% | 69.4% |
  | 31B on the same table (LiveCodeBench, Tau2) | 80.0% | 76.9% |

  E4B is 4.5B effective parameters (8B with per-layer embeddings); 12B is 11.95B dense. Our own measurement agrees: E4B
  solved 3/23 dev tasks on the VM, quitting early.
- **Why 12B did not serve (notebook 11, Oct 14).** The model was the allowed `gemma-4-12b-it-qat-w4a16-ct` (path
  `/kaggle/input/models/google/gemma-4/other/gemma-4-12b-it-qat-w4a16-ct/2`).
  - **The cause:** the competition wheelhouse's vLLM 0.19.1 has no native `Gemma4UnifiedForConditionalGeneration`. It fell back
    to its generic Transformers backend (`Resolved architecture: TransformersMultiModalForCausalLM`).
  - **Where it crashed:** in that fallback, in `modeling_gemma4_unified.py` during vLLM's memory-profiling forward, with
    `ValueError: Expected hidden_size to be 3840, but found: 256`. 256 is the attention head dimension, so a per-head norm
    met a norm built for the full hidden size.
  - **Likely not fixed by tp 1 (inference):** the module replacement happens regardless of tensor-parallel size.
  - **The probable fix is a newer competition wheelhouse.** The organizers wrote that they are "working on adding support for
    the other Gemma 4 dense variants (e2b, e4b, and 12b)". When the wheelhouse is re-uploaded, re-run notebook 11 first.
