### 3.3 Which code do the tests import? (vm-a2 Docker sandbox, Oct 11 09:33)

Evidence: `b0_gold_import_check.jsonl` (this folder), produced by `scripts/planB/b0_import_check.py`.
For each task it builds a Phase-2 sandbox with the same calls, in the same order, as swegemma 0.2.11
`verify_task` (wheels, snapshot, synthetic hardware, git exclude, editable install, test deps,
workspace test config, baseline commit), then imports the package under test from plain Python and
from inside a pytest run in the task's `tests/` directory, and reports the file imported.

| Task | Imported under pytest | Installed (pip show) | Repo snapshot version | Verdict |
| --- | --- | --- | --- | --- |
| requests_7315 | `requests 2.34.2`, `/usr/local/lib/python3.13/site-packages/requests/` | 2.34.2, site-packages | 2.33.1 | workspace shadowed |
| requests_7427 | `requests 2.34.2`, site-packages | 2.34.2, site-packages | 2.34.0.dev1 | workspace shadowed |
| fastapi_15661 | import fails: site-packages `pydantic/errors.py` -> `No module named 'typing_inspection'` | fastapi 0.141.1, site-packages | 0.136.3 | released copy installed, and broken |
| fastapi_15588 | same import failure | fastapi 0.141.1, site-packages | 0.136.1 | released copy installed, and broken |
| rich_4070 | `/workspace/rich/__init__.py` | 14.3.3, editable at `/workspace` | n/a | workspace tested (correct) |

Readings:

- **requests**: the tests exercise the released `requests-2.34.2` wheel from `wheels/`, not the task's
  code. An agent's edits cannot change the outcome. A task passes with an empty patch exactly when
  the release already contains its fix: checked directly by unpacking `requests-2.34.2` and running
  both tasks' key assertions against it (7315: `request_url` returns `//v:h`; 7427:
  `should_bypass_proxies("http://prelocalhost/", ...)` is False), which matches their empty-patch
  passes (`1 passed`; `216 passed, 13 skipped`, the same 13 skips as A2, so skips are not the cause).
  A2, which tests the repo code in its own venv, saw both tests fail before the fix.
- **fastapi**: the sandbox installs the released `fastapi-0.141.1` wheel instead of the repo, and that
  copy cannot be imported (pydantic 2.13.4 without `typing_inspection`, section 3.1). Every fastapi
  task whose tests import fastapi fails with or without a patch. `fastapi_15661` resolved in the smoke
  only because its fix and test touch `scripts/prepare_release.py` and never import fastapi (empty run:
  `No module named 'scripts.prepare_release'`; gold run: `16 passed`).
- **rich**: the editable install works; pytest imports `/workspace/rich`. (Plain `python3 -c` from
  `/workspace` with `PYTHONSAFEPATH=1` imports the site-packages copy, but pytest's rootdir handling
  puts the workspace first, and pytest is what scores.)
- Mechanism (inferred from the 0.2.11 source, not traced line by line): `install_editable_package`
  runs `pip install --no-index --find-links=/wheels --no-build-isolation --no-deps -e /workspace
  2>/dev/null || true`, so a failed editable build is silent; the test-dependency step then streams
  released wheels, including the package under test, into site-packages.
- Consequence: in the public Docker sandbox only rich tasks (48) measure an agent's patch. Gold-pass
  exclusions for requests and fastapi are environment artifacts, not task defects.

Open (blocks Plan B denominators): which environment scores submissions? Kaggle has no Docker, so
runs on Kaggle use the subprocess sandbox, which inherits the notebook host's site-packages (a
different set: the host has pydantic 2.13.5 and `typing_inspection` 0.4.4, section 3.1). The hidden
scorer may also use a private wheel cache. Plan B's denominators must come from the scoring
environment. Next check, on Kaggle: run the gold pass in the subprocess sandbox on a few requests and
fastapi tasks and print the imported file the same way (`b0_import_check.py` with
`SubprocessManager` in place of `ContainerManager`).
